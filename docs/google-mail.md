# Сервисные письма через Google Apps Script

Владелец сообщил, что Brevo не принимает его российский номер для проверки аккаунта. У владельца уже есть Gmail. Для Render выбран вариант с собственным небольшим веб-приложением Google Apps Script: backend подписывает запрос, скрипт проверяет подпись и вызывает MailApp. Покупать домен, Workspace или передавать пароль Gmail сайту не требуется.

Это подготовленный способ для небольшого запуска. Реальный аккаунт Google и доступность публикации проверяются отдельно; локальные тесты не доказывают, что скрипт уже опубликован. Для обычного Gmail Google указывает квоту **100 получателей за сутки**, общую с другими скриптами аккаунта. Письмо отправляется с Gmail владельца скрипта с именем «ПромтМаркет», а не с `promtmarket@mail.ru`. MailApp не читает почтовый ящик. Квоты могут меняться; отправка не даёт гарантии попадания во входящие.

## Подготовка локального файла

Для новой конфигурации:

```powershell
backend/.venv/Scripts/python.exe deploy/prepare_render.py
```

Если `.local/render.env` уже был подготовлен с Brevo:

```powershell
backend/.venv/Scripts/python.exe deploy/prepare_google_mail.py
```

Второй скрипт сохраняет базу, ключи подписи и шифрования, переключает `MAIL_DELIVERY` на `google_apps_script` и добавляет `GOOGLE_MAIL_SECRET`. Повторный запуск не меняет существующий секрет. `LEGAL_READY=false` остаётся без изменения. Оба скрипта работают только с частной конфигурацией и не публикуют сервисы, не отправляют писем.

## Действия владельца в Google

1. Открыть [Google Apps Script](https://script.google.com/home) под своим Gmail и создать **Новый проект / New project**. Назвать его `PromtMarket Mail`.
2. Открыть локальный `deploy/google-mail/Code.gs`, скопировать его целиком и заменить содержимое файла `Code.gs` в редакторе Google. Сохранить проект. В код не вставлять пароли и секреты.
3. Открыть шестерёнку **Настройки проекта / Project Settings**. В **Свойства скрипта / Script Properties** добавить свойство с именем `GOOGLE_MAIL_SECRET`.
4. Значение свойства взять из строки `GOOGLE_MAIL_SECRET` в `.local/render.env`: копировать только значение после `=`, **без окружающих одинарных кавычек**. Сохранить свойство. Не использовать для этого CSRF_SECRET или AUTH_PROXY_SECRET.
5. Вернуться в редактор, выбрать функцию **authorizeMail** в верхнем списке и нажать **Выполнить / Run**. Google попросит разрешение на отправку писем от вашего имени. Это собственный проект с предоставленным кодом. Эта функция только проверяет остаток квоты, письмо не отправляет. Приложение использует разрешение `script.send_mail`; чтение писем не требуется. При желании можно включить показ манифеста в настройках и использовать приложенный `deploy/google-mail/appsscript.json`, где scope указан явно.
6. Нажать **Развернуть → Новое развертывание / Deploy → New deployment**. Через шестерёнку типа выбрать **Веб-приложение / Web app**.
7. Выбрать **Выполнять от моего имени / Execute as: Me** и **У кого есть доступ: Все / Who has access: Anyone**, включая доступ без входа в Google. Подпись каждого запроса проверяется самим скриптом. Если вариант Anyone отсутствует, не считать настройку завершённой: нужно проверить ограничения этого аккаунта.
8. Нажать **Развернуть / Deploy** и скопировать **URL веб-приложения**, оканчивающийся на `/exec`. Нужен полный адрес `https://script.google.com/macros/s/.../exec`, а не просто идентификатор развертывания и не тестовая ссылка `/dev`.
9. Вставить адрес в `GOOGLE_MAIL_URL` частного `.local/render.env`, сохранить файл. В чат секрет и файл конфигурации не присылать.

Развёртывание скрипта и согласие Google выполняет владелец аккаунта. При изменении `Code.gs` после публикации создать новую версию через **Manage deployments → Edit → New version**, сохранив существующее развертывание и его URL.

## Проверка без отправки письма

После заполнения URL выполнить из корня:

```powershell
backend/.venv/Scripts/python.exe deploy/check_google_mail.py
```

Проверка подписывает операцию `check`, проверяет соответствующий идентификатор в ответе и выводит только статус и остаток квоты. Ни адреса получателей, ни сообщения она не отправляет. Проверка не требует переключать `LEGAL_READY`: это отдельная диагностика транспорта, а не обход проверки запуска приложения.

Открытие URL `/exec` обычной ссылкой в браузере выполняет GET и вернёт `post_required`. Это ожидаемый ответ, не ошибка настройки. Авторизованный backend отправляет POST, а запросы без верной подписи не принимаются.

## Что реализовано

- Фиксированный формат запроса: JSON с полями `payload` и `signature`. Payload — строка JSON с `op`, `id` и Unix-временем `issued_at`; для отправки дополнительно `to`, `subject`, `text`. Подпись HMAC-SHA256 вычисляется по точным UTF-8 байтам payload и передаётся в hex. Общий секрет не передаётся в URL или теле запроса.
- Принимаются запросы не старше пяти минут, одному получателю, с ограничениями на размеры и заголовки. Скрипт не является открытым сервером произвольной отправки без аутентификации.
- Script Lock сериализует отправки. После успешного вызова MailApp сохраняются только ID задачи и время, без адресов, текста и ссылок; повторная задача с тем же ID распознаётся. Метки удаляются через семь дней. Если процесс завершится между отправкой и записью ID, строго однократная отправка не гарантируется.
- Backend разрешает только HTTPS endpoint `script.google.com/macros/s/.../exec`. ContentService может вернуть redirect: допускается один последующий GET только к `script.googleusercontent.com`, без повторной передачи POST-тела и подписи. Остальные перенаправления отклоняются, сертификаты проверяются.
- Успех подтверждается по JSON `ok: true` и совпадающему ID задачи, а не только по HTTP 200. Это подтверждение принятия MailApp, не доставки в почтовый ящик.
- При ошибке сохраняется существующая зашифрованная очередь писем и общий предел повторов. Если дневная квота исчерпана и попытки закончились, сообщение требует отдельного разбора очереди; автоматического гарантированного ожидания до следующих суток нет.
- SMTP, Brevo и локальная доставка сохранены как отдельные режимы. Пароль Gmail, cookies Google и OAuth refresh token в Render не сохраняются. Используется стандартный проект Apps Script с авторизацией владельца.

Локально проверены подписи, ограничения запроса, повторы, отказ при неверной подписи, квоты и ошибки через подменённые MailApp и HTTP. Владелец опубликовал Web app и дал разрешение Google. Выполнена реальная подписанная операция `check`: аутентификация прошла, Google вернул квоту 100 получателей, URL сохранён в частном `.local/render.env`. Проверка не отправляла письма. Фактическая доставка сообщения ещё не проверена. Документы магазина ещё являются шаблонами; production-проверки и отключение реальных платежей сохранены.
