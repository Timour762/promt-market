# Render Free и Neon: подготовка публикации

Выбран один бесплатный Web Service Render. Для первой публикации владелец выбрал публичную витрину без регистрации и оплаты: запускается только Next.js с публичным снимком каталога. Полный режим позднее запускает Next.js, FastAPI и почтовый worker в одном контейнере с PostgreSQL в Neon. Эта схема не расходует бесплатные часы сразу на два отдельных Web Service. После простоя сервис засыпает; постоянная ссылка не означает гарантированную доступность или отсутствие квот.

## Первая публикация: витрина

Добавить в Render переменную **`PUBLIC_PREVIEW=true`**. Уже импортированные секреты не менять; `LEGAL_READY=false` и `PLATEGA_ENABLED=false` сохранить. Проверить остальные поля по таблице ниже, затем нажать **Deploy web service**. После сборки дождаться состояния **Live** и открыть фактический HTTPS-адрес, назначенный Render.

В этом режиме supervisor не запускает миграции, backend или почтовый worker. Next.js читает `frontend/src/lib/preview-catalog.json`: только публичные поля шести опубликованных карточек, без полных текстов, пользователей или заказов. Цена бизнес-промпта 500 ₽ сохранена из публичного локального API. Изменения в базе не обновляют этот снимок автоматически.

Главная остаётся с прежним баннером. Поиск, фильтры, карточки, изображения, примеры и контакты доступны. Вместо входа — ссылка «Витрина», вместо покупки — «Покупки скоро откроются». Серверный middleware разрешает только публичные страницы и ресурсы, закрывает API аккаунтов, библиотеки, заказов и платежей и отклоняет все изменяющие запросы. `/api/ready` проверяет готовность web без базы. Сеансовые cookies не устанавливаются. Документы будущих продаж остаются черновиками; страница конфиденциальности описывает текущий режим. Витрина передаёт `X-Robots-Tag: noindex, nofollow`.

Для перехода к полному магазину сначала завершить документы и сведения о продавце, проверить Neon, загрузить каталог и создать отдельного облачного администратора, проверить доставку писем и подключить Platega. Затем установить `LEGAL_READY=true` и `PUBLIC_PREVIEW=false`. Сам флаг витрины не ослабляет production-проверки backend. Пока он включён, webhook Platega недоступен и продажи открывать нельзя.

## Поля формы Render

### Включение аккаунтов, цены 500 ₽ (23.10.2026)

У всех шести товаров цена 500 ₽ (`50000` копеек): и в снимке витрины, и в исходном каталоге. Миграция `0011_catalog_prices` обновляет цены существующих карточек, не меняя исторические заказы или полные тексты. В полном серверном режиме supervisor сначала запускает `python -m app.bootstrap`: миграции и идемпотентное добавление шести публичных карточек. Аккаунты и закрытые тексты из локальной базы не переносятся.

Для режима аккаунтов нужны `PUBLIC_PREVIEW=false`, `REGISTRATION_READY=true`, `LEGAL_READY=false`, `PLATEGA_ENABLED=false`. Сохраняются проверки HTTPS, защищённых cookies, подписи IP, CSRF и настроенной почты. В этом режиме покупатели могут зарегистрироваться, войти, подтвердить email и восстановить пароль. Сервер отклоняет создание заказов до открытия продаж; на карточках отображается подготовка покупок. Владелец: Эскиев Тимур Бухариевич, физическое лицо; контакт по предоставленным данным — `promtmarket@mail.ru`.

`REGISTRATION_READY` — отдельный технический флаг запуска аккаунтов, не подтверждение соответствия законодательству или готовности продаж. Настройки размещения персональных данных и применимые требования необходимо проверить до их публичного сбора. Подготовленная Neon находится в США, а Gmail передаёт адреса и письма Google; это прямо описано на странице конфиденциальности. Черновики условий продаж не объявлены действующей офертой.

Финальная сборка Next.js успешна. Четыре изолированных браузерных сценария на компьютере и телефоне проверили регистрацию → кабинет → выход → повторный вход и восстановление; реальные письма не отправлялись. Исправлена отправка формы до hydration: `method=post`, поля и submit выключены до готовности JavaScript, пароль не попадает в URL. Шесть сценариев standalone-витрины прошли; 24 различных backend-теста проверили почту, безопасность аккаунтов, цены и запрет новых заказов/ручного подтверждения оплаты в режиме аккаунтов. Все тестовые схемы очищены.

Локальная PostgreSQL обновлена до `0011_catalog_prices`; все шесть карточек по 500 ₽. Проверены изолированные миграции, сохранение истории, роли, CSRF, закрытие заказов в режиме аккаунтов и почтовая конфигурация. Google mail прошёл проверку аутентификации без отправки письма. Neon ответил на read-only `SELECT 1` через официальный HTTPS SQL endpoint с проверкой TLS: реквизиты действительны, в `public` пока 0 таблиц. Прямой TCP-доступ из этой сети нестабилен; миграции должны выполниться из окружения Render. Для смены режима на Render нужны сохранение переменных и успешный запуск; до этого публичная регистрация не считается включённой. Отдельный частный файл `.local/render-accounts.env` подготовлен с прежними ключами и выключенной оплатой, исходная конфигурация витрины не изменена.

| Поле | Значение |
| --- | --- |
| Source Code | Репозиторий `Timour762/promt-market` с опубликованными изменениями подготовки |

Python-команды `pip install -r requirements.txt` и `gunicorn ...` не используются. После выбора Docker соответствующие поля формы меняются. Параметры Docker и проверки состояния могут находиться в Advanced.

Не нажимать Deploy до проверки наличия подготовленных файлов в выбранной ветке GitHub и заполнения частной конфигурации. Сам выбор репозитория в Render не публикует локальные изменения Git. Ветка Render должна совпадать с веткой актуального приложения: `codex/database-catalog`.

## Частная конфигурация

Из корня проекта один раз выполнить:

```powershell
backend/.venv/Scripts/python.exe deploy/prepare_render.py
```

Скрипт читает `.local/neon.env`, создаёт `.local/render.env` и генерирует отдельные ключи подписи и шифрования для нового размещения, включая секрет Google mail. Локальный `backend/.env`, локальные аккаунты и пароли не используются. Существующий выходной файл не перезаписывается: ключи нельзя случайно менять при повторной подготовке. Если файл уже был создан с Brevo, выполнить `backend/.venv/Scripts/python.exe deploy/prepare_google_mail.py`: этот помощник сохранит существующие ключи и базу. Оба файла исключены из Git, `.local` также исключена из Docker context.

Для полного магазина перед импортом через Render **Add from .env** опубликовать собственный скрипт Gmail и заполнить `GOOGLE_MAIL_URL`; секрет `GOOGLE_MAIL_SECRET` должен совпадать со свойством в скрипте. Почта уже подготовлена. `LEGAL_READY=false` оставлен намеренно: пользователь подтвердил, что документы пока являются шаблонами. Этот флаг нельзя переключать ради обхода проверки запуска backend. Первая витрина с `PUBLIC_PREVIEW=true` запускается отдельно, без backend, базы и писем.

Render передаёт `RENDER_EXTERNAL_URL`. Supervisor использует его как HTTPS-адрес сайта, если `PUBLIC_WEB_URL` не задан, и заполняет соответствующие списки допустимых источников запросов для web и API. Для своего домена адрес и allowlists задаются явно; подставлять домен, угаданный только по имени сервиса, не требуется.

Для web-процесса supervisor также устанавливает `AUTH_CLIENT_IP_SOURCE=render`. Проверка входа использует один корректный IP из `CF-Connecting-IP`, который, согласно [официальной инструкции Render](https://render.com/articles/host-pocketbase-on-render), перезаписывается входным прокси. Первому адресу из пользовательского `X-Forwarded-For` на Render не доверяем; при отсутствии корректного заголовка запрос отклоняется. Существующая схема VPS с Caddy продолжает использовать своё прежнее определение адреса.

Все секреты вводить в локальном файле или закрытых Environment Variables Render, без публикации в чате, GitHub или скриншотах. Не пересоздавать ключи шифрования после начала работы магазина.

## Почта через существующий Gmail

Render Free блокирует исходящие SMTP-порты 25, 465 и 587, поэтому прежний SMTP Mail.ru для этого размещения не подходит. Первый вариант с Brevo не удалось активировать: владелец сообщил, что его российский номер не поддерживается при подтверждении аккаунта. После подтверждения наличия Gmail подготовлен транспорт Google Apps Script через HTTPS.

Следовать [пошаговой инструкции Google mail](google-mail.md): добавить `deploy/google-mail/Code.gs` в собственный проект, сохранить секрет в Script Properties, дать разрешение на отправку и опубликовать Web app от имени владельца с доступом Anyone. Затем сохранить `/exec` URL в `.local/render.env` и выполнить `backend/.venv/Scripts/python.exe deploy/check_google_mail.py`. Эта проверка не отправляет письма. Владелец уже опубликовал скрипт: реальная подписанная проверка прошла, URL сохранён локально, Google вернул остаток квоты 100 получателей. Фактическая доставка письма пока не проверена. Для обычного Gmail лимит общий с другими скриптами аккаунта.

Backend подписывает запрос HMAC, проверяет TLS и разрешает только Google endpoint с одним контролируемым ContentService redirect без повторной отправки тела. Скрипт проверяет подпись, время запроса, одного адресата и повторы задач. Успех — совпадающий ID в JSON-подтверждении, а не только HTTP 200. SMTP, Brevo и локальный режим остались доступными в коде. Никаких паролей Gmail или OAuth refresh token в Render не сохраняется.

## Neon и первоначальные данные

Приложение и Alembic принимают обычную строку Neon `postgresql://...?...sslmode=require&channel_binding=require`. Общий helper преобразует драйвер в asyncpg, проверяет сертификат и имя сервера и сохраняет hostname для SNI. Опция libpq `channel_binding` в asyncpg не поддерживается: helper удаляет её с явным предупреждением, сохраняя проверенный TLS. Принудительная привязка SCRAM к TLS этим драйвером не обеспечивается.

На этом компьютере подключение к Neon пока завершалось таймаутом. Пароль и SQL-запросы не проверены; после появления окружения Render соединение нужно проверить оттуда. Недоступность из локальной сети нельзя выдавать за подтверждённую ошибку учётных данных.

Перед запуском API supervisor выполняет `alembic upgrade head`. При ошибке миграции web и worker не запускаются. Supervisor не создаёт администратора, не переносит локальные аккаунты и не выполняет seed каталога. Необходимо отдельно согласовать и загрузить каталог с закрытыми версиями промптов и создать администратора с новым паролем. Существующая команда `python -m app.seed` остаётся отдельной операцией; перед её использованием проверяются источник и состав данных. Бесплатный Render не даёт интерактивный Shell, поэтому первоначальное наполнение следует выполнить отдельно с компьютера, имеющего доступ к Neon, либо подготовить явную одноразовую процедуру.

Platega остаётся отключённой до подключения магазина и получения ключей. После активации адрес уведомлений будет `https://адрес-сайта/api/payments/platega/webhook`. Настройка вывода USDT выполняется в Platega.

## Проверки и оставшиеся ограничения

- Сборка Next.js прошла локально. Шесть браузерных проверок готовой standalone-сборки (компьютер и телефон) прошли с флагом витрины, установленным только при запуске, и недоступным backend: каталог, изображения, цена, поиск, страницы документов, отсутствие cookies, блокировка закрытых страниц и всех изменяющих запросов. Две проверки обычного режима магазина также прошли.
- 17 unit-тестов преобразования URL/TLS, почты и production-проверок, 5 тестов частного env, 9 тестов supervisor и 6 проверок определения IP прошли. Регрессионные проверки безопасности и Platega: ещё 15 тестов прошли на изолированных схемах локальной PostgreSQL с подменёнными внешними платежами и почтой.
- После добавления витрины 12 проверок supervisor прошли, один POSIX-тест завершения группы процессов пропущен на Windows. Проверено, что витрина не запускает миграции, API или почту, а обычный режим сохраняет прежний порядок запуска.
- Docker локально не установлен: полный образ ещё не собирался и в Linux/Render не запускался. Потребление памяти на бесплатном инстансе ещё не измерено.
- Дополнительно проверены подпись и обработка ответов Google mail, свойства/авторизация скрипта через подменённые Google services и безопасное переключение частной конфигурации без изменения ключей.
- Реальная аутентификация Google mail и чтение квоты проверены без отправки письма. Доставка писем, соединение Render → Neon, первоначальная загрузка каталога и публичный HTTPS пока не проверены.
- Документы и данные продавца остаются черновиками. Проверки production не обойдены.
