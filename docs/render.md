# Render Free и Neon: подготовка публикации

Выбран один бесплатный Web Service Render: Next.js, FastAPI и существующий почтовый worker запускаются в одном контейнере. PostgreSQL находится в Neon. Эта схема не расходует бесплатные часы сразу на два отдельных Web Service. После простоя сервис засыпает; постоянная ссылка не означает гарантированную доступность или отсутствие квот.

## Поля формы Render

| Поле | Значение |
| --- | --- |
| Source Code | Репозиторий `Timour762/promt-market` с опубликованными изменениями подготовки |
| Name | `promt-market`, либо другое доступное имя |
| Language | `Docker` |
| Branch | Ветка, в которую опубликованы файлы подготовки; сейчас изменения только локальные |
| Region | `Virginia (US East)`, ближе к созданной базе Neon в AWS US East 1 |
| Root Directory | Пусто |
| Dockerfile Path | `deploy/render/Dockerfile` |
| Docker Build Context | `.` |
| Docker Command | Пусто: используется CMD образа |
| Compute | Только `Free`, `$0/month` |
| Health Check Path | `/api/ready` |

Python-команды `pip install -r requirements.txt` и `gunicorn ...` не используются. После выбора Docker соответствующие поля формы меняются. Параметры Docker и проверки состояния могут находиться в Advanced.

Не нажимать Deploy до публикации подготовленных файлов в выбранную ветку и заполнения частной конфигурации. Сам выбор репозитория в Render не публикует локальные изменения Git.

## Частная конфигурация

Из корня проекта один раз выполнить:

```powershell
backend/.venv/Scripts/python.exe deploy/prepare_render.py
```

Скрипт читает `.local/neon.env`, создаёт `.local/render.env` и генерирует отдельные ключи подписи и шифрования для нового размещения, включая секрет Google mail. Локальный `backend/.env`, локальные аккаунты и пароли не используются. Существующий выходной файл не перезаписывается: ключи нельзя случайно менять при повторной подготовке. Если файл уже был создан с Brevo, выполнить `backend/.venv/Scripts/python.exe deploy/prepare_google_mail.py`: этот помощник сохранит существующие ключи и базу. Оба файла исключены из Git, `.local` также исключена из Docker context.

Перед импортом через Render **Add from .env** опубликовать собственный скрипт Gmail и заполнить `GOOGLE_MAIL_URL`; секрет `GOOGLE_MAIL_SECRET` должен совпадать со свойством в скрипте. `LEGAL_READY=false` оставлен намеренно: пользователь подтвердил, что документы пока являются шаблонами. Этот флаг нельзя переключать ради обхода проверки запуска. До готовности почты и документов production не стартует.

Render передаёт `RENDER_EXTERNAL_URL`. Supervisor использует его как HTTPS-адрес сайта, если `PUBLIC_WEB_URL` не задан, и заполняет соответствующие списки допустимых источников запросов для web и API. Для своего домена адрес и allowlists задаются явно; подставлять домен, угаданный только по имени сервиса, не требуется.

Для web-процесса supervisor также устанавливает `AUTH_CLIENT_IP_SOURCE=render`. Проверка входа использует один корректный IP из `CF-Connecting-IP`, который, согласно [официальной инструкции Render](https://render.com/articles/host-pocketbase-on-render), перезаписывается входным прокси. Первому адресу из пользовательского `X-Forwarded-For` на Render не доверяем; при отсутствии корректного заголовка запрос отклоняется. Существующая схема VPS с Caddy продолжает использовать своё прежнее определение адреса.

Все секреты вводить в локальном файле или закрытых Environment Variables Render, без публикации в чате, GitHub или скриншотах. Не пересоздавать ключи шифрования после начала работы магазина.

## Почта через существующий Gmail

Render Free блокирует исходящие SMTP-порты 25, 465 и 587, поэтому прежний SMTP Mail.ru для этого размещения не подходит. Первый вариант с Brevo не удалось активировать: владелец сообщил, что его российский номер не поддерживается при подтверждении аккаунта. После подтверждения наличия Gmail подготовлен транспорт Google Apps Script через HTTPS.

Следовать [пошаговой инструкции Google mail](google-mail.md): добавить `deploy/google-mail/Code.gs` в собственный проект, сохранить секрет в Script Properties, дать разрешение на отправку и опубликовать Web app от имени владельца с доступом Anyone. Затем сохранить `/exec` URL в `.local/render.env` и выполнить `backend/.venv/Scripts/python.exe deploy/check_google_mail.py`. Эта проверка не отправляет письма. Владелец уже опубликовал скрипт: реальная подписанная проверка прошла, URL сохранён локально, Google вернул остаток квоты 100 получателей. Фактическая доставка письма пока не проверена. Для обычного Gmail лимит общий с другими скриптами аккаунта.

Backend подписывает запрос HMAC, проверяет TLS и разрешает только Google endpoint с одним контролируемым ContentService redirect без повторной отправки тела. Скрипт проверяет подпись, время запроса, одного адресата и повторы задач. Успех — совпадающий ID в JSON-подтверждении, а не только HTTP 200. SMTP, Brevo и локальный режим остались доступными в коде. Никаких паролей Gmail или OAuth refresh token в Render не сохраняется.

## Neon и первоначальные данные

Приложение и Alembic принимают обычную строку Neon `postgresql://...?...sslmode=require&channel_binding=require`. Общий helper преобразует драйвер в asyncpg, проверяет сертификат и имя сервера и сохраняет hostname для SNI. Опция libpq `channel_binding` в asyncpg не поддерживается: helper удаляет её с явным предупреждением, сохраняя проверенный TLS. Принудительная привязка SCRAM к TLS этим драйвером не обеспечивается.

На этом компьютере подключение к Neon пока завершалось таймаутом. Пароль и SQL-запросы не проверены; после появления окружения Render соединение нужно проверить оттуда. Недоступность из локальной сети нельзя выдавать за подтверждённую ошибку учётных данных.

Перед запуском API supervisor выполняет `alembic upgrade head`. При ошибке миграции web и worker не запускаются. Supervisor не создаёт администратора, не переносит локальные аккаунты и не выполняет seed каталога. Необходимо отдельно согласовать и загрузить каталог с закрытыми версиями промптов и создать администратора с новым паролем. Существующая команда `python -m app.seed` остаётся отдельной операцией; перед её использованием проверяются источник и состав данных. Бесплатный Render не даёт интерактивный Shell, поэтому первоначальное наполнение следует выполнить отдельно с компьютера, имеющего доступ к Neon, либо подготовить явную одноразовую процедуру.

Platega остаётся отключённой до подключения магазина и получения ключей. После активации адрес уведомлений будет `https://адрес-сайта/api/payments/platega/webhook`. Настройка вывода USDT выполняется в Platega.

## Проверки и оставшиеся ограничения

- Сборка Next.js прошла локально.
- 17 unit-тестов преобразования URL/TLS, почты и production-проверок, 5 тестов частного env, 9 тестов supervisor и 6 проверок определения IP прошли. Регрессионные проверки безопасности и Platega: ещё 15 тестов прошли на изолированных схемах локальной PostgreSQL с подменёнными внешними платежами и почтой.
- Один POSIX-тест завершения группы процессов пропущен на Windows.
- Docker локально не установлен: полный образ ещё не собирался и в Linux/Render не запускался. Потребление памяти на бесплатном инстансе ещё не измерено.
- Дополнительно проверены подпись и обработка ответов Google mail, свойства/авторизация скрипта через подменённые Google services и безопасное переключение частной конфигурации без изменения ключей.
- Реальная аутентификация Google mail и чтение квоты проверены без отправки письма. Доставка писем, соединение Render → Neon, первоначальная загрузка каталога и публичный HTTPS пока не проверены.
- Документы и данные продавца остаются черновиками. Проверки production не обойдены.
