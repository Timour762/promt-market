# Подготовка размещения

Для выбранного бесплатного размещения Render + Neon используется отдельная [инструкция Render](render.md). Описанный ниже Docker Compose предназначен для VPS, а не для формы Render Web Service.

Подготовлены Dockerfile для API и Next standalone, deploy/compose.yaml: PostgreSQL, миграции, API, mail-worker, web и Caddy TLS. Docker окружение ещё не запускалось. Инфраструктура не оплачена и не создана.

На выбранном сервере в РФ: получить исходники, скопировать deploy/.env.example в deploy/.env и заполнить частную конфигурацию, настроить A/AAAA DNS, открыть 80/443 и ограничить SSH. Не открывать PostgreSQL/API наружу. DATABASE_URL и POSTGRES_PASSWORD должны совпадать, специальные символы пароля в URI должны быть закодированы. Сгенерировать CSRF_SECRET и Fernet ключ без публикации. LEGAL_READY=false намеренно блокирует production до завершения документов; не выставлять true только ради старта.

После готовности конфигурации из корня проекта сначала проверить её без вывода секретов: `docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet`. Затем запустить: `docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build`. Параметр `--env-file` нужен для подстановки переменных Compose из `deploy/.env`; `env_file` у контейнеров решает другую задачу. Никакого автосоздания админа с известным паролем. Администратор создаётся отдельной командой с интерактивным скрытым паролем. Локальный admin-пароль не переносить в production. Seed каталога выполняется отдельной операцией после просмотра исходников, не при каждом старте. Миграции применяются до API и mail-worker. SQLite не используется.

Резервное копирование: BACKUP_DIR=/private/backups sh deploy/backup.sh под системным планировщиком сервера. Копии должны быть зашифрованы на уровне хранилища, доступны только ответственному лицу, перенесены на отдельное хранилище; сроки хранения согласовать. Перед запуском выполнить восстановление в отдельную тестовую БД: pg_restore --no-owner --dbname=<изолированная БД> <копия>, проверить число/связность записей. Скрипт не удаляет старые копии. Ключ MAIL_ENCRYPTION_KEY хранить отдельной защищённой копией, иначе очередь писем не расшифровать.

Логи: контейнерные stdout/stderr, API без access-log, ошибки не содержат паролей/токенов/тел писем. Настроить ротацию Docker logs и мониторинг доступности публичного /api/ready (внутренний API /ready) и страниц сайта, оповещения об ошибках SMTP/БД. Обработчик уведомлений Platega подготовлен; реальные платежи выключены до подключения магазина, настройки ключей и публичного HTTPS-адреса. Данные Platega вносятся в частный `deploy/.env`; URL уведомлений: `https://ваш-домен/api/payments/platega/webhook`. Caddy выдаёт TLS только при правильном публичном DNS. Возврат релиза не восстанавливает БД; перед миграциями резервная копия и план прямого исправления схемы.


AUTH_PROXY_SECRET должен быть случайным секретом не короче 32 символов, одинаковым у API и web. Caddy является единственным публичным входом и формирует X-Forwarded-For; web подписывает непрозрачный идентификатор для разделения ограничений входа по клиентам. API не доверяет входящему IP/header без подписи. Не публиковать порты web/API и не добавлять недоверенный прокси без отдельной настройки доверенных адресов. Текущий limiter хранится в памяти единственного процесса API; перед несколькими API-процессами/репликами нужен общий Redis/PostgreSQL backend для ограничений. API/web имеют healthchecks, web ждёт готовый API. Для текущего малого запуска один процесс указан явно.
