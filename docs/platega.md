# Platega: оплата в RUB, расчёты и выплаты USDT

Для новых заказов используется платёжная страница Platega. Покупатель нажимает «Оплатить», оплачивает рублями через СБП (paymentMethod=2) и возвращается в магазин. Страница проверяет статус автоматически. Промпт открывается только после серверной проверки CONFIRMED, суммы, валюты, Merchant ID, transaction ID и связи платежа с заказом. Переход по return URL сам по себе доступ не открывает. Уведомления и повторные запросы обрабатываются без повторной выдачи или дублирования журнала.

Кабинет Platega пока не создан, реальные платежи не включены. Локальные проверки используют вымышленный API и отдельные временные схемы PostgreSQL. Существующая карта магазина не используется при создании новых платежей Platega.

## Подключение магазина

1. Оставить заявку на [официальном сайте Platega](https://platega.io/ru), согласовать условия и пройти подключение магазина.
2. Согласовать с Platega конвертацию RUB → USDT, комиссии, сеть, адрес криптокошелька и порядок выплат. Выводы управляются на стороне Platega. Приложение не хранит seed-фразу и не выполняет вывод USDT через недокументированный API. Поле amountUsdt в истории платежей показывает данные сервиса, а не подтверждение отправки средств на кошелёк.
3. Получить Merchant ID и API Secret в кабинете Platega и внести их в закрытый `backend/.env`:

```dotenv
PLATEGA_ENABLED=false
PLATEGA_MERCHANT_ID=<UUID магазина>
PLATEGA_SECRET=<API Secret>
PUBLIC_WEB_URL=https://ваш-домен
```

4. Настроить публичный HTTPS-домен магазина и callback URL в кабинете Platega: `https://ваш-домен/api/payments/platega/webhook`. Localhost не подходит для доставки уведомлений. Callback проксируется в FastAPI с заголовками X-MerchantId и X-Secret, затем сервис повторно запрашивает транзакцию у Platega.
5. Применить миграции, перезапустить backend, включить `PLATEGA_ENABLED=true` и проверить один согласованный платёж, выдачу промпта и возврат. Статус настройки доступен в `/account` и `/admin/payments`. Отсутствие ключей или публичного HTTPS-адреса оставляет кнопку оплаты выключенной.

```powershell
# Из backend
.venv\Scripts\python.exe -m alembic upgrade head
```

Секрет никогда не передаётся клиентскому JavaScript и не возвращается административным API. В `/admin/payments` показываются только признаки наличия настроек и история транзакций.

## Повторные попытки и возвраты

Platega генерирует ID транзакции; документация создания checkout не описывает ключ идемпотентности. Приложение сначала сохраняет намерение создать платёж. Если запрос завершился неоднозначно, повторный платёж автоматически не создаётся: требуется сверка в Platega. Имеющаяся открытая ссылка используется повторно. После подтверждённого EXPIRED/CANCELED/FAILED можно создать новую попытку, предыдущая остаётся в истории.

CHARGEBACKED закрывает доступ, если у заказа нет другого подтверждённого платежа. Старое подтверждение не отменяет уже обработанный возврат. На обеих страницах неоплаченного заказа используется Platega, включая старые заказы со статусом awaiting_confirmation. При нажатии «Оплатить» старый ручной заказ переключается на Platega в одной транзакции с созданием попытки оплаты; подтверждение администратора для него больше не действует. История ручного перевода сохраняется. Если Platega ещё не подключена, состояние заказа и старые записи не меняются.

## Проверки

```powershell
# Из backend
.venv\Scripts\python.exe -m unittest tests.test_security tests.test_platega -v

# Из frontend
npm.cmd run typecheck
npm.cmd run test:payments
npm.cmd run build
```

Браузерный стенд использует отдельные порты 3117/8117, временную схему, вымышленные реквизиты и перехваченную страницу pay.platega.io. Он не создаёт реальные платежи. При аварийном завершении после остановки стенда: `.venv\Scripts\python.exe -m tests.manual_payment_server --cleanup` из backend.
